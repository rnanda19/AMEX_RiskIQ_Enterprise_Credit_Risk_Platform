# Production Monitoring (Platform-Wide)

Real, current scope, verified 2026-09-09 (`find . -iname monitoring_job.py`,
`git grep`).

## What exists today

**Problem 1 (Credit Scoring / PD Prediction)** has a real, runnable
scheduled monitoring job:
`01_Problem1_Credit_Scoring_PD_Prediction/src/monitoring/monitoring_job.py`,
generated by `12_monitoring.ipynb`. It is intended to run as a daily cron
job / Windows Task Scheduler task (`python monitoring_job.py
--new-data-csv path/to/new_scored_batch.csv`), compares a new scored batch
against the real `monitoring_baseline.json` this platform's own holdout
run produced, and exits non-zero (so a scheduler can act on the exit
code, e.g. fail the job / send a page) if any monitored feature or the
model's output distribution has drifted into an ALERT state. It reuses
the real saved `preprocessing_artifacts.joblib` and champion model to
score the new batch consistently with how the champion model was
originally trained and evaluated.

**No other problem (2 through 14) has an equivalent monitoring job.**
This is a real, current gap -- not yet closed.

## What "monitoring" does NOT mean here

This is drift/quality monitoring of a batch of predictions against a
saved baseline -- it is not:

- A live metrics/observability stack. There is no Prometheus, Grafana, or
  OpenTelemetry integration anywhere in this repository (`git grep -c`
  for each returns 0).
- An alerting integration (Slack, PagerDuty, email). The job's own exit
  code is the only signal today; wiring that to a real notification
  channel is a real, not-yet-started item.
- Champion/challenger or canary deployment monitoring. That pattern is
  discussed narratively in Problem 1's
  `notebooks/07_model_risk_management.ipynb` but has no real
  implementation anywhere in the platform.

## The honest path to platform-wide monitoring

The correct next step is not to write 13 more from-scratch monitoring
scripts -- it's to extract Problem 1's `monitoring_job.py` into a
shared, parameterized module (baseline path, feature list, and champion
model path as arguments) that each problem's own hardening pass can then
adopt with a few lines of problem-specific config. That refactor is
tracked in `ROADMAP.md` and has not yet been started.
